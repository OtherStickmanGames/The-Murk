# The Murk — правила проекта

Мобильная 3D-колония с обороной в воксельном мире: вертикальный экран, Android. Горстка изгнанников строит форпост вокруг Очага и отбивает набеги, пока поселенцы сами работают и учатся.

- Дизайн игры — `docs/GDD.md`. Перед задачей прочитай разделы, которых она касается.
- Текущие задачи — `docs/tasks/M<N>.md` (этапы M0–M7 описаны в GDD, раздел «MVP и дорожная карта»).
- Общение с автором — на русском.

## Стек

- Unity 6000.6.2f1, URP (для телефона — `Assets/Settings/Mobile_RPAsset.asset`), C#.
- Input System (уже установлен), Unity Test Framework.
- Интерфейс — UI Toolkit (UXML/USS или код), не uGUI. Настройки панели — `Assets/Game/UI/Settings/GamePanelSettings.asset`, эталон 1080×1920, масштаб по ширине.
- Burst, Collections, Mathematics и Newtonsoft.Json должны быть явно прописаны в `Packages/manifest.json`, а не держаться на зависимостях других пакетов.
- Цель — Android: IL2CPP, ARM64, только портретная ориентация.
- Новые пакеты не добавлять без согласия автора.
- Репозиторий: `origin` → `github.com/OtherStickmanGames/The-Murk`, основная ветка — `master`. Бинарные файлы (картинки, звук, модели, шрифты) идут через Git LFS по правилам в `.gitattributes`.

## Структура

```
Assets/Game/
  Sim/     Game.Sim   (без UnityEngine): мир, воксельные данные, поселенцы, работы, бой, экономика, сохранения
  Gen/     Game.Gen   (без UnityEngine): генерация региона по сиду
  Voxel/   Game.Voxel : меши чанков (Burst), перестройка при изменении блоков
  View/    Game.View  : модели, анимации, камера, эффекты
  UI/      Game.UI    : экраны, шторки, жесты
  Data/    JSON-описания контента (загрузка через Resources: Data/Resources/Defs/)
  DevTools/    Game.DevTools    : отладочная консоль, счётчик FPS и читы
  App/         Game.App         : точка входа Bootstrap — единственное место, где системы связываются
  EditorTools/ Game.EditorTools : только редактор — сборка сцены Bootstrap, настройки проекта, сборка APK (меню «The Murk»)
Assets/Scenes/Bootstrap.unity   единственная сцена, собирается из кода
Assets/Tests/EditMode/          тесты Sim и Gen
docs/                           GDD и задачи
```

Каждая папка с кодом — отдельный asmdef. У `Game.Sim` и `Game.Gen` стоит `noEngineReferences: true`.

Ссылки между сборками: Gen → Sim; Voxel → Sim; View → Sim, Voxel; UI → Sim, View; DevTools → Sim, UI; App → все; EditorTools → App.

Пространства имён `Game.Debug` и `Game.Editor` не заводить: внутри `Game.*` они перекрывают `UnityEngine.Debug` и `UnityEditor.Editor`.

Хранилище блоков в `Game.Sim` — на обычных массивах: `NativeArray` живёт в UnityEngine. Для Burst `Game.Voxel` копирует данные чанка в `NativeArray`.

## Архитектура — обязательно

- **Симуляция отдельно от отображения.** Логика живёт в `Game.Sim` и не знает о сцене и MonoBehaviour. Отображение читает состояние симуляции, а не наоборот.
- **Фиксированный тик:** 10 шагов симуляции в секунду игрового времени. Ускорение x2/x3 прогоняет больше шагов, а не увеличивает шаг.
- **Детерминизм:** один сид — один и тот же мир. Случайность только через собственный генератор с сидом, никакого `UnityEngine.Random` в симуляции.
- **Контент только в данных.** Предметы, рецепты, здания, блоки, навыки, черты, враги, события — JSON, как Def-файлы в RimWorld. В коде никаких захардкоженных чисел баланса.
- **Данные читает Unity, разбирает симуляция.** Слой Unity загружает JSON через Resources и передаёт в `Game.Sim` текст, а не пути к файлам. Разбор — через Newtonsoft.Json: `JsonUtility` — часть UnityEngine, в симуляции он недоступен.
- **Одна точка входа.** Сцена `Bootstrap` создаёт мир и связывает системы. Без синглтонов и `FindObjectOfType`: зависимости передаются явно.
- **Сцены собираются из кода** или через Unity CLI; YAML сцен и префабов руками не править.

## Код

- Код и комментарии — на английском, тексты игры — в JSON-данных.
- Имена: `PascalCase` для типов и публичных членов, `_camelCase` для приватных полей.
- Один класс — один файл, файлы до 300–400 строк. Разрастается — дели.
- Комментарии только там, где неочевидно «почему».

## Проверка

- Тесты `Game.Sim` и `Game.Gen` — в EditMode. Запускай их через Unity CLI после каждой правки логики: `unity test "<проект>" --mode EditMode --output <файл.xml>`.
- Сборка APK из командной строки (редактор с этим проектом должен быть закрыт): `Unity.exe -batchmode -nographics -quit -projectPath "<проект>" -buildTarget Android -executeMethod Game.EditorTools.AndroidBuild.Build -logFile <лог>`. APK ложится в `Builds/Android/TheMurk.apk`.
- Основная проверка — в редакторе: Play Mode с Device Simulator в портретном разрешении телефона. Только на телефоне проверяются жесты (мультитач) и производительность. Опиши автору, что и как проверить.
- Отладочная консоль с первого дня: вызвать набег, выдать ресурсы, x10, вылечить всех и т. п. Новая система — новые команды консоли.

## Модели и эффорт

Модель и эффорт выбирает автор при открытии сессии, сама сессия их не меняет. Составляя список задач этапа, указывай у каждой задачи рекомендуемую модель и эффорт по этой таблице:

| Тип задачи | Модель | Эффорт |
| --- | --- | --- |
| Каркас проекта, основы архитектуры, ревью архитектуры | Opus 5.5 | max |
| Основные системы: воксели, работы, поиск пути, бой, сохранения | Opus 5.5 | xhigh |
| Экраны интерфейса, мелкие фичи, правки по отзыву | Opus 5.5 | high |
| Тяжёлый баг после двух неудачных попыток | Opus 5.5 | max |
| Пачки контента в JSON по готовой схеме | Sonnet 5 | medium |

## Порядок работы над задачей

1. Прочитай задачу в `docs/tasks/M<N>.md` и нужные разделы GDD.
2. Крупная задача (новая система, больше 5 файлов) — сначала план и структура классов, код после одобрения автора.
3. Реализуй, прогони тесты, проверь сборку.
4. Отчитайся коротко: что сделано, как проверить (в редакторе или на телефоне), что осталось или вызывает сомнения.
5. Когда автор подтвердил, что работает: отметь задачу в чек-листе, сделай коммит и отправь его в `origin` (`git push`).
6. Если по ходу меняется дизайн — обнови `docs/GDD.md` в той же задаче.

Не делай в задаче того, о чём не просили. Заметил проблему вне задачи — напиши о ней, но не чини молча.

## Шаблон задачи

Так автор ставит задачи; если чего-то не хватает — спроси.

```
Задача: <что сделать, одним предложением>
Контекст: docs/GDD.md, раздел «...»; файлы: ...
Готово, когда: <что видно в редакторе или на телефоне, или какой тест проходит>
Ограничения: <что не трогать; без новых пакетов; контент только через JSON>
Сначала план, код после одобрения.   ← для крупных задач
```

Отзыв после проверки автор пишет по схеме «сделал X, ожидал Y, получилось Z», иногда со скриншотом или записью экрана.
